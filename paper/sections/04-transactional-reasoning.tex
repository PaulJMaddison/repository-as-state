\section{From Stateful Agents to Transactional High-Capability Reasoning}
\label{sec:transactional}

RaS treats a high-capability reasoning episode as a bounded transaction over durable external engineering state:
\begin{equation}
R_t + U_t
\rightarrow
\text{reasoning transaction}
\rightarrow
\text{validated state transition}
\rightarrow
R_{t+1}.
\end{equation}
After $R_{t+1}$ is accepted, the reasoning state may be destroyed.

The word \emph{transactional} describes lifecycle and durability, not ACID database semantics. A reasoning episode does not automatically provide serialisability, atomic side effects, isolation, or deterministic replay. The analogy is narrower: a bounded computation reads authoritative state, attempts a transition, and only a validated result becomes durable programme state.

This reframing changes the scalable unit from a permanent long-lived intelligent agent process to an \emph{independent reasoning transaction}. Several potential systems properties follow, although none is yet an empirical RaS result.

\paragraph{Restartability.}
A fresh reasoner can in principle be scheduled after a crash, timeout, policy boundary, model upgrade, or ordinary task completion if the repository captures sufficient continuity.

\paragraph{Horizontal scheduling.}
Reasoning transactions need not maintain affinity to the inference worker that performed a previous transaction. This may simplify scheduling over shared model infrastructure, provided reconstruction is efficient.

\paragraph{Model interchangeability and routing.}
Because the continuity substrate is external, a later transaction can in principle use a different model. Model-routing work such as RouteLLM demonstrates that capability/cost routing is a distinct optimisation problem \citep{ong2024routellm}. RaS does not require learned routing, but it creates a clean transaction boundary at which routing decisions can be made.

\paragraph{Fault tolerance.}
If uncommitted reasoning disappears, the accepted repository state remains. This resembles a general durable-compute pattern in which volatile workers reconstruct from persisted state. Durable Functions, for example, formalises reliable workflow execution under compute--storage separation and record/replay \citep{burckhardt2021durable}. RaS does not inherit those guarantees; the precedent shows only that volatile compute over durable state is a well-established systems pattern.

\paragraph{Lifecycle clarity.}
A transaction has an explicit start state, task, allowed context, execution boundary, validation rule, and accepted end state. These boundaries improve experimental control because the continuity intervention can be defined precisely.

The architecture also exposes failure classes. A fresh transaction can fail because $\Gamma$ reconstructed the wrong files; because the reasoner misunderstood correctly reconstructed state; because the work package omitted a critical constraint; because the executor implemented it incorrectly; because the environment failed; or because the validator was invalid. Collapsing all of these into “agent failed” would obscure the mechanism.

The strongest objection remains semantic underspecification. Persistent agents can carry intentions that never became durable artefacts. A transactional architecture forces the system either to encode those intentions or to accept that a reset may lose them. This is not an implementation bug in the research design; it is precisely what Forced-State-Reset Evaluation is intended to expose.

Transactional reasoning is therefore a lifecycle hypothesis, not a claim that agents should be stateless internally. During one transaction a model can use substantial working context, tools, scratch state, and iterative reasoning. RaS asks only whether that state needs to remain persistent \emph{between} accepted engineering transitions.
