\section{Forced-State-Reset Evaluation and Experimental Method}
\label{sec:method}

The central experimental contribution is \emph{Forced-State-Reset Evaluation}: deliberately destroy the reasoning session between sequential engineering stages and test whether the next fresh reasoner can reconstruct enough state to continue correctly.

For a sequence of tasks:
\begin{align}
A_1 + R_0 + U_1 &\rightarrow R_1,\\
\text{destroy }A_1, \qquad
A_2^{\mathrm{fresh}} + R_1 + U_2 &\rightarrow R_2,\\
\text{destroy }A_2, \qquad &\ldots
\end{align}
The fresh process receives the current repository state, current task, and stable experiment instructions. It must not receive the previous conversation, a hidden summary, a resumed session, copied state reconstruction, or future history.

The purpose is direct: determine whether engineering continuity resides sufficiently in $R_t$ rather than $H_t$.

\subsection{Experimental conditions}

\input{tables/experiment-conditions}

\paragraph{A --- Persistent monolithic control.}
One continuing high-capability session retains conversation/history and may reason, edit, and test.

\paragraph{B --- RaS forced reset.}
The same high-capability model and configuration is used, complete allowed repository state persists, and a new session begins after every bounded task with no previous session state.

\paragraph{C --- RaS semantic-state ablation.}
Condition C follows B but removes selected semantic state carriers according to a preregistered manifest. The purpose is to identify which repository artefacts contribute to continuity. Ablation must account for redundant information: deleting one document does not remove a decision if a later test or comment reveals the same fact.

\paragraph{D --- RaS tiered execution.}
High-capability reasoning is transactional while a separate lower-cost, stateful, or local executor performs constrained implementation. The reasoner re-enters only when protocol-defined evidence requires escalation. Because D adds a second causal variable, P0 may focus primarily on A/B/C and evaluate D later.

\subsection{P0 --- Forced-State-Reset Pilot}

P0 is a pilot, not a confirmatory study. It will use a complex real-world private software repository under controlled local conditions while keeping source and raw proprietary evidence outside this public repository. Public outputs will contain only sanitised aggregate evidence and publication-safe metadata.

The intended pilot should select approximately five sequential, non-trivial historical engineering tasks; construct isolated starting histories; create neutral task specifications; compare persistent and reset conditions; optionally include semantic-state ablation; run hidden behavioural verification; and capture all measurable reconstruction and execution telemetry.

P0 has not been run as part of this paper.

\subsection{Preventing future-history leakage}

Historical task reconstruction is methodologically dangerous. Simply checking out an old commit from a complete Git clone is insufficient because future commits containing the solution may remain accessible in refs, reflogs, packfiles, object databases, local branches, tags, or remotes.

The experimental repository must therefore contain only history allowed through the intended $R_0$ boundary. Future solution SHAs must be non-resolvable. Remotes must be absent or made incapable of revealing future state. Hidden task-generation material must not be accessible from the workspace. The harness should fail closed when prohibited future history can be resolved.

This requirement is stronger than ordinary benchmark checkout hygiene because RaS is explicitly testing whether repository state is sufficient. Leakage of future repository state would invalidate the central intervention.

\subsection{No human rescue}

Controlled runs must prohibit hints, “look in file X” guidance, copied information from another condition, manual repair, prompt improvement after observing a failure, or transfer of previous-agent conclusions. Otherwise the human operator becomes an unmeasured continuity channel.

Negative results must remain evidence. The study should distinguish:
\begin{itemize}
    \item \textbf{agent failure}: the required experimental environment was available, but the reasoner or executor failed to produce an accepted transition;
    \item \textbf{harness/infrastructure failure}: the run could not validly test the agent because required infrastructure, isolation, telemetry, or tooling failed.
\end{itemize}
The exclusion rule for infrastructure failure must be preregistered before outcomes are observed.

\subsection{State-reconstruction probe}

Before editing after a reset, the fresh reasoner should produce the structured probe defined in Section~\ref{sec:resumability}. The probe records architecture, behaviour, components, constraints, tests, completed work, required work, evidence paths, uncertainty, and unknowns without requesting chain-of-thought. It is stored outside the subject repository so it does not become durable state for the next task.

\subsection{Outcome and telemetry}

Primary outcomes should include correct task continuation under independent behavioural verification and RRI by sequential depth. Secondary outcomes should include reconstruction accuracy, regression rate, RTF, total model input/output tokens, cached/uncached input where exposed, files read, repository searches, tool/model calls, elapsed reconstruction and task time, retries, escalation, and human-intervention flags.

Task success should not be defined by visible tests alone. Visible tests are themselves candidate semantic state carriers and can invite overfitting. Hidden verification, held-out behavioural tests, or another independent preregistered acceptance criterion should adjudicate correctness.

P0 is expected to inform later sample-size and power decisions. Confirmatory experiments should preregister estimands, confidence intervals, missing-data rules, multiplicity control, randomisation or counterbalancing, and model/version pinning to the extent providers permit.
