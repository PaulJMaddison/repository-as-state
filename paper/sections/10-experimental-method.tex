\section{Forced-State-Reset Evaluation and Experimental Method}
\label{sec:method}

The central experiment deliberately removes predecessor reasoning-session continuity after an \emph{accepted} engineering transition and tests whether a fresh reasoner can continue a dependent programme from the same durable project state.

The publication record now includes two bounded Subject-B results. P1 is the methodology-corrected three-task controlled study; P2 is the accepted Level-2 same-repository replication with four tasks, three repetitions, two conditions and 12 matched task-by-repetition pairs. Their results are reported separately and are not pooled. The P2 analysis preserves the distinction between no observed A/B difference and successful task performance: both P2 conditions reached the correctness floor.

\subsection{Causal target}

The primary P0 comparison is:

\paragraph{A --- Persistent-history control.}
The high-capability reasoner has access to the predecessor conversation/session history relevant to the task chain.

\paragraph{B --- RaS forced reset.}
A fresh high-capability reasoning session receives no predecessor conversation, hidden summary, copied reconstruction, resume state, or account/session memory.

The intended A/B treatment is \textbf{availability of predecessor reasoning-session history}. Everything else that can materially affect the outcome must be matched or explicitly measured.

Condition C, semantic-state ablation, is exploratory and should remove only a small preregistered information class. Tiered execution D is deferred beyond the primary P0 because changing executor capability would confound the continuity intervention.

\subsection{Canonical task-boundary materialisation}

Before \emph{every task in both A and B}, the harness must materialise the exact accepted repository state $R_t$ into a canonical clean workspace. Persistent condition A must not inherit untracked files or tool residue merely because its conversation persists.

The following must be invariant across A/B unless the protocol explicitly treats them as measured variables:
\begin{itemize}
    \item repository commit/object graph allowed at the boundary;
    \item tracked and untracked workspace contents;
    \item system/developer experiment instructions;
    \item current task text;
    \item high-capability model identifier/build, sampling configuration, and tool schema;
    \item executor implementation and privileges;
    \item base image, language/toolchain versions, environment variables, locale, clock/timezone policy, and dependency versions;
    \item network policy;
    \item hidden verifier and acceptance rule.
\end{itemize}

Shell history, editor/IDE state, temporary files, worktrees, previous-agent scratch files, local databases, generated summaries, and environment artefacts must be reset or identically seeded. Build/dependency caches may be used only under a preregistered policy that makes them condition-independent (for example, deterministic prewarming from the same cutoff state); otherwise they must be reset.

If the selected model interface can carry undisclosed account-level or cross-session memory that cannot be disabled or audited, the A/B experiment is \textbf{not identifiable} on that interface. Prefer a stateless API or controlled local runtime in which the message sequence and system instructions are explicit.

\subsection{Prompt and cache controls}

The stable experimental instructions and current-task prompt must be byte-identical across A/B except for the explicit predecessor-history payload in A. Prompt/context caching is not itself the behavioural treatment. Where possible, disable cross-run cache effects for strict causal analysis; otherwise record exposed cached/uncached token counters and separate behavioural results from economic interpretation.

\subsection{FUTURE_HISTORY_LEAK_GATE}

Simply checking out an old commit from a complete clone is invalid. Before any model call, the harness must verify a fail-closed \texttt{FUTURE_HISTORY_LEAK_GATE}. At minimum:

\begin{itemize}
    \item all remotes are absent;
    \item every known post-cutoff solution SHA fails object-resolution checks;
    \item no local branch, tag, reflog, packed object, or alternate object store exposes future history;
    \item \texttt{.git/objects/info/alternates} and equivalent environment-based alternate-object mechanisms are absent;
    \item no worktree or filesystem link points to the source repository;
    \item no patch file, generated diff, hidden task-generation artefact, or CI artefact contains future code;
    \item network policy prevents fetching the private source repository or other task-specific future state.
\end{itemize}

If any gate check fails: \textbf{RUN INVALID --- STOP BEFORE MODEL INVOCATION}. The failing gate remains part of the audit record.

\subsection{Task leakage and corpus construction}

Information legitimately present in $R_t$ at the cutoff is allowed even if helpful. Leakage is information from after the cutoff or task-generation material that reveals the future solution.

Historical tasks can leak through future commit messages, issue edits, branch names, changelogs, TODOs, generated documentation, future tests, or hidden patch files. Corpus preparation must audit these channels.

To reduce retrospective cherry-picking, P0 must define before runs:
\begin{itemize}
    \item a candidate historical time/window or other reproducible sampling frame;
    \item explicit inclusion and exclusion criteria;
    \item a rule requiring genuine sequential dependence between later tasks and earlier accepted code, interface, test, architecture decision, or state transition;
    \item a committed candidate list and task hashes;
    \item the sampling/randomisation procedure and seed where randomness is used;
    \item any subjective complexity labels before outcomes are observed.
\end{itemize}

Five unrelated bug fixes are not a strong continuity test. Artificially manufacturing dependency to favour RaS is also invalid.

\subsection{Hidden behavioural verification}

Each task's verifier must:
\begin{itemize}
    \item live outside the experimental workspace and be unavailable to the agent;
    \item be frozen before runs with a version identifier and cryptographic hash;
    \item be identical across A/B/C for the same task;
    \item test externally intended behaviour rather than patch-text similarity;
    \item accept equivalent correct implementations;
    \item avoid using the historical future patch as the sole oracle.
\end{itemize}

The historical implementation may inform task selection and verifier construction, but it is not the required textual solution.

\subsection{No human rescue and rerun rules}

After a run starts, prohibit hints, file pointers, copied information, prompt adjustment, manual edits, transfer of conclusions across conditions, and selective reruns because an outcome is disappointing.

Pre-register:
\begin{itemize}
    \item timeouts and stopping conditions;
    \item allowed retry count and whether retries remain inside the same experimental unit;
    \item \textbf{AGENT_FAILURE}: the controlled environment was valid but the agent failed to reach an accepted state;
    \item \textbf{INFRASTRUCTURE_FAILURE}: a preregistered harness/runtime failure prevented a valid agent test;
    \item exact conditions under which an infrastructure-failed run may be repeated.
\end{itemize}

Excluded and repeated runs remain auditable.

\subsection{P0 interpretation}

P0 is a methodology pilot/initial case study, likely involving roughly five dependent tasks. It is not powered to establish general superiority or non-inferiority. Before running it, the preregistration must allow only:
\begin{itemize}
    \item \textbf{METHODOLOGY FAILURE};
    \item \textbf{EVIDENCE AGAINST RaS};
    \item \textbf{MIXED / CONDITIONAL PILOT EVIDENCE};
    \item \textbf{SUPPORTIVE PILOT EVIDENCE}.
\end{itemize}
“Proven” is not an allowed P0 interpretation.

\subsection{Outcome and telemetry}

Primary behavioural reporting should compare matched A/B verifier outcomes task-by-task and by depth. Also report complete-sequence success. RRI remains descriptive for B. The reconstruction probe and resource vector in Sections~\ref{sec:resumability} and~\ref{sec:cost} provide mechanism and efficiency information.

P0 should capture reconstruction and total input/output tokens, files/bytes read, searches, model/tool calls, elapsed times, retries, cache counters where exposed, and human/intervention flags. Classification rules must be frozen before outcomes.

Only after repeated tasks/runs exist should confirmatory work preregister a non-inferiority/equivalence margin, confidence intervals, dependence-aware analysis, multiplicity handling, and statistical power.
