\section{Tiered Execution}
\label{sec:tiered}

Software-engineering agents frequently combine two categories of work: high-level reasoning and machine interaction. The former includes architecture, decomposition, causal diagnosis, difficult debugging, review, interpretation, and planning. The latter includes file editing, compilation, test execution, formatting, Git operations, and constrained infrastructure interaction.

A monolithic design can perform both categories with the same high-capability model. RaS asks whether they can be separated. Let $N_R$ be the number of high-capability reasoning units and $N_E$ the number of execution units. If the high-capability resource has unit cost $c_R$, a simple monolithic model is
\begin{equation}
C_{\mathrm{monolithic}} = (N_R + N_E)c_R.
\end{equation}
If execution can instead use a lower-cost worker with unit cost $c_E$, plus orchestration overhead $C_O$,
\begin{equation}
C_{\mathrm{tiered}} = N_Rc_R + N_Ec_E + C_O.
\end{equation}
Under this theoretical model, tiering reduces cost when
\begin{equation}
N_E(c_R-c_E) > C_O.
\label{eq:tieredcondition}
\end{equation}

Equation~\ref{eq:tieredcondition} is deliberately provider neutral. It does not assert any model price, inference cost, margin, or hardware utilisation. Real systems introduce further terms: retries, specification errors, executor failures, tool latency, model-call minimums, and the cost of escalating a failed execution back to a high-capability reasoner.

Tiered execution can fail in at least four ways. First, the work package may be semantically incomplete. Second, the executor may lack the reasoning ability to recover from an unexpected repository state. Third, repeated execution failures may consume more resources than a monolithic agent. Fourth, coordination itself may increase latency and token use.

These failure modes make condition D an empirical question rather than an architectural preference. A useful experiment should compare outcome-normalised resource use, not just per-call price. A cheap executor that creates regressions or requires repeated high-capability intervention is not economically cheaper in the relevant sense.

Tiering also changes state placement. The execution worker may be stateful with respect to the local workspace and tools while the high-capability reasoner remains ephemeral between reasoning transactions. This is compatible with the central RaS proposition: the expensive reasoning process need not carry the programme's durable continuity.

The design arose from practical workflows in which a human or high-capability model decomposed work and a comparatively shallow coding agent performed edits, builds, tests, and Git interaction. Again, this observed workflow is motivation only. Controlled evaluation must hold task definitions, repository state, and acceptance criteria constant while varying persistence and execution tier.

If successful, tiering would imply that the most intelligent component need not be the component that performs the most operations. That separation is economically interesting, but it is equally important for security, discussed in Section~\ref{sec:security}.
