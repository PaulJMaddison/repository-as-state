\section{Future Work}
\label{sec:future}

The immediate next step after paper v0.1 is an independent audit of the theoretical foundation, experiment design, claims register, and literature positioning before P0 is frozen. The purpose of that audit is to find hidden assumptions, leakage routes, ambiguous outcome definitions, and prior work that weakens the novelty boundary.

After that audit, P0 corpus selection and preregistration should identify a small sequence of genuinely dependent engineering tasks, pin allowed historical state, construct neutral task specifications, define hidden behavioural verification, freeze the reconstruction-cost classification, and verify that future solution history is non-resolvable. The preregistration should be committed before any P0 outcomes are observed.

A second phase should replicate the evaluation on public repositories. Public subjects reduce the reproducibility limitation of the initial private pilot and allow independent groups to reproduce the reset intervention. Replication should vary language, repository size, test quality, documentation maturity, task locality, dependency width, and architectural complexity.

A third phase should deepen semantic-state ablation. Rather than treating the repository as a single memory substrate, experiments can selectively remove architecture decisions, agent instruction files, issue-derived state, tests, schemas, comments, build rules, or Git history while keeping the task definition stable. The objective is to identify which artefact combinations most strongly support resumability.

A fourth phase should evaluate tiered execution separately. Executor capability, tool access, work-package granularity, retry policy, and escalation policy can be varied. Outcome-normalised cost must include failed executions and high-capability re-entry rather than only nominal per-call price.

A fifth phase should directly test reconstruction scaling. Synthetic repository growth can add irrelevant mass while holding task semantics constant. Real tasks can vary dependency width. Retrieval methods can compare plain search, symbol indexes, static-analysis graphs, task-specific manifests, and model-guided exploration. The bounded-reconstruction hypothesis should be replaced by measured growth curves.

Cross-model evaluation is also necessary. Repository sufficiency may depend on the reasoner's code-navigation and inference capabilities. A well-structured repository might reduce dependence on any one provider's memory system, but this remains an untested benefit.

Security work should evaluate malicious repository instructions, poisoned documentation, confused-deputy attacks, executor compromise, policy enforcement, and human approval boundaries. The security advantage of separating intelligence from privilege requires direct adversarial evidence.

Finally, the broader Authoritative-State Externalisation Principle in Section~\ref{sec:authoritative-principle} should remain speculative until analogous experiments exist outside software engineering. CRM systems, databases, ticket systems, event logs, document stores, and infrastructure state may provide authoritative substrates in other domains, but RaS does not prove that they are sufficient.
